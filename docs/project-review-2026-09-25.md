## 후속 변경: 프로덕션 빌드 해결

D:가 exFAT여서 일반 파일의 `readlink`가 EISDIR를 반환하고 junction 생성도 지원하지 않는 것이 원인이었다. `npm run build`에 파일시스템 감지와 지원되는 임시 볼륨에서의 Webpack 빌드를 추가했다. 의존성은 Windows 병렬 복사로 준비하고, 성공한 산출물만 원래 프로젝트 `.next`에 반영한다. 환경 파일 자체는 복사하지 않으며 의존성 패키지와 디스크 포맷은 수정하지 않는다.

- `npm run build`: 종료 코드 0. 컴파일, TypeScript 검사, 정적 페이지 25개 생성, 실행 의존성 수집 완료.
- `npm run test:build`: 종료 코드 0. D: 프로젝트에서 프로덕션 서버를 띄워 공개 목록·상세 페이지, 진단, 로그인, 가이드, 사이트맵, 이미지, JavaScript 파일 및 관리자 비로그인 접근 차단을 검증했다.
- 결과물의 `appDir`와 `outputFileTracingRoot`는 `D:\opencollege`이며 임시 빌드 폴더는 정리됐다.

위 빌드와 실행 검증은 `DATABASE_URL`을 비운 기본 콘텐츠 환경에서 수행했다. 실제 운영 DB·메일 서비스 연결을 검증한 것은 아니다. 사용 방법은 `docs/build.md`에 정리했다. 아래의 빌드 실패 기록은 수정 전 상태다.

## 우선순위별 발견

1. **높음 — 초기 관리자 설정에 소유 확인 부재.** `lib/actions.ts:123`의 `setupAdminPassword`는 관리자 이메일 문자열과 비밀번호 조건만 검사한다. 관리자 비밀번호가 아직 없는 새 DB 또는 초기화 상태에서는 이메일을 아는 미인증 사용자가 비밀번호를 먼저 설정하고 관리자 세션을 받을 수 있다. 일회성 설정 토큰이나 소유 확인이 필요하다. 이미 비밀번호가 설정된 운영 DB가 이 조건인지 확인하지 않았다.
2. **높음 — 업로드 API에 세션 폐기 검증 누락.** `app/api/admin/upload/route.ts:11`은 `lib/auth.ts:88`의 서명·만료 검증만 사용한다. 비밀번호 변경으로 sessionVersion을 높여도 기존 쿠키는 만료 전 업로드에 사용할 수 있다. 관리자 인증 검증을 통일해야 한다.
3. **높음 — DB 조회 실패 시 폐기 검증 생략.** `lib/auth.ts:111`은 세션 버전 조회 오류를 삼키고 서명 검증만으로 통과시킨다. 폐기된 쿠키도 조회 장애 중 인증 관문을 통과할 수 있다. 이후 DB 작업의 성공 여부는 별개다. 인증 조회 실패 시 접근을 거부해야 한다.
4. **중간 — 공개 이메일 발송에 호출 제한 부재.** `lib/check-actions.ts:264`의 `emailMyResult`는 이메일 형식과 답변만 검사한 후 지정 주소로 메일을 발송한다. 코드 내 수신인 확인·발송 횟수 제한이 없어 반복 요청에 따른 발송량 및 비용 증가가 가능하다. 실제 배포 인프라의 별도 제한은 확인하지 않았다.
5. **중간 — 전역 로그인 잠금 유발 가능.** `lib/actions.ts:178`의 로그인 로직은 잘못된 이메일도 전역 실패 횟수에 더한다. 임의 입력 5회로 정상 관리자까지 10분 동안 로그인할 수 없게 만들 수 있다. 공격자별 호출 제한과 잠금 정책을 함께 보완해야 한다.
6. **중간 — 검증 및 DB 설치 절차 미비.** `package.json:9`의 `next lint`는 실행 시 `Invalid project directory ... opencollege\\lint`로 실패한다. test/typecheck 스크립트도 없다. `drizzle.config.ts:5`는 `./drizzle`을 지정하지만 수동 SQL은 `migrations/`에 있고 기존 기본 테이블에 대한 ALTER부터 포함되어 있다. 빈 DB 구성부터 업그레이드까지 재현 가능한 절차를 정해야 한다.
